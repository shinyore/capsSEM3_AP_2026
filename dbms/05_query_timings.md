# AP DBMS CP4 Query Timings

## Setup and workload

The benchmark ran against the isolated PostgreSQL database `skillbridge_ap_cp4` on PostgreSQL 16.15 (client 16.15), using a local PostgreSQL cluster under `/private/tmp`, Unix socket `/private/tmp/skillbridge-ap-cp4-socket`, port `55439`, user `shine`. The database was created from the AP schema in `dbms/03_schema.sql`; that schema creates 18 tables, 9 enum types, and 25 indexes. The cluster is local benchmark infrastructure, not a production database.

No CP4 rubric or repeat count is included in this repository. To provide repeatable measurements, each of the 79 statements was run three times using `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)`. The report records average, median, minimum, and maximum execution time from PostgreSQL's `Execution Time` line. Each execution used a fixed representative parameter set documented in `dbms/07_benchmark_queries.py`. This is one synthetic workload and one parameter set per query; it is not a multi-parameter or concurrency study.

All statements were executed inside `BEGIN` / `ROLLBACK`. For the 39 WRITE queries, `EXPLAIN ANALYZE` executed the write so its plan and runtime were measured, then rollback prevented the change from persisting. The final row-count and benchmark-ID checks confirmed no benchmark writes leaked into the fixture. READ statements used the same transaction wrapper for consistent execution handling.

## Summary and reproducibility

- **Queries benchmarked:** 79 total: 40 READ and 39 WRITE.
- **Runs:** 3 per query, 237 successful `EXPLAIN ANALYZE` executions in total.
- **Plans:** `dbms/plans/R01.txt`–`R40.txt` and `dbms/plans/W01.txt`–`W39.txt`; every file has three run sections. `dbms/plans/summary.csv` contains the same aggregate timings.
- **Runner:** `dbms/07_benchmark_queries.py` substitutes representative parameters from its local mapping and captures PostgreSQL plans. It accepts database, host, port, user, and run count as arguments.
- **Fixture:** `dbms/06_synthetic_data.sql` loads deterministic synthetic rows; its committed transaction ends with `ANALYZE`.

Re-run only in a fresh database after applying `dbms/03_schema.sql`; the schema script is not idempotent:

```sh
psql -h /private/tmp/skillbridge-ap-cp4-socket -p 55439 -U shine \
  -d skillbridge_ap_cp4 -X -v ON_ERROR_STOP=1 -f dbms/06_synthetic_data.sql
python3 dbms/07_benchmark_queries.py \
  --database skillbridge_ap_cp4 \
  --host /private/tmp/skillbridge-ap-cp4-socket \
  --port 55439 --user shine --runs 3
```

The benchmark completed with no query failures. This report does not change `dbms/04_queries.sql` or existing CP2/CP3 design artifacts.
